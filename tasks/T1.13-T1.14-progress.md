# T1.13 and T1.14 implementation

These tasks follow ADR-011 and the Phase 1A service-area amendment. T1.14 means
pending request creation from `todo.md`; acceptance is T1.16.

## Implementation

- T1.13: authenticated, commute-specific public driver profile and mobile detail
  screen. Validate rider ownership and current requestability for a targeted
  driver. Return public vehicle and verification information, rating distribution
  and paginated anonymous verified reviews. Exclude private route geometry,
  starting location, roster, contacts and documents.
- T1.14: authenticated `POST /subscriptions` with a required `Idempotency-Key`,
  server-side ownership/coverage/availability checks, price snapshot, independent
  requested leg windows, and a 24-hour response deadline. Store PENDING only;
  no seat, run, slot, trip or billing allocation.
- Additive schema migration separates requested terms from agreed service fields.
  Pending requests leave agreed timestamps and next billing date unset.
- Public API documentation is generated from the new shared response contracts.

## Remaining lifecycle scope

The mobile request form/submission integration is T1.22. Profile navigation does
not send a request. Driver preview, acceptance, expiry and withdrawal remain their
separate Phase 1B tasks. Native-device verification remains required before task
completion is recorded.

## Migration and rollout

`20261022T1503_pending_subscription_requests` adds the snapshot/deadline fields and
indexes, permits unset legacy agreement fields, and checks snapshot/deadline
pairing plus unbilled new PENDING requests. Existing legacy records are preserved.
The full migration chain was replayed in the dedicated database. The development
database was not migrated or reseeded during this implementation.

Before running the new request endpoint against a different database, confirm its
target and apply the checked migration chain using
`pnpm --filter @routeride/api prisma:migrate`. Deploy the migration before the API.
Rebuild shared contracts before starting dependent applications. Native device
layout, font scaling, screen-reader and authenticated live-flow verification are
still required before checking these tasks off.

## Live verification — 2026-10-31

Ran the real matching service (port 8001) and built API (port 3100) against the dedicated database `routeride_city_filter_test_20261027`, seeded with one consumer, one rider and three approved drivers (established route, route-free, distant corridor). Requests used HS256 tokens minted with the project's JWT secret. All 26 checks passed; the seeded rows were then removed (0 left) and both services stopped.

- **Authorization:** search without a token 401; driver token 403; another consumer using this rider 403 for search, profile and request creation.
- **Search (T1.12 data):** all three drivers returned, including the distant corridor driver (5.7 km from the route, not vetoed); route-free driver has null distances and `UNSET` route state; price is integer paisas with currency; no scores or private fields in the public response.
- **Profile (T1.13):** 200 for a requestable driver; no route geometry, start location, contacts or licence; a stranger's rider is refused. `plateNumber`, `vehicleYear` and `photoUrl` are intentionally public (see the open question below).
- **Request creation (T1.14):** missing key 400; driver role 403; valid request 201 `PENDING`, deadline exactly 24 h, price snapshot recorded, `reviewStatus: REQUIRED`; same key and body replays the same request; same key with a different body 422; a lower-ranked distant driver can be requested; out-of-city endpoint refused; 6 concurrent identical requests produced exactly one request. A repeat run with fresh keys returned 409, confirming duplicate-intent protection.
- **Database effects:** the PENDING rows had no billing date, no agreed times, no Stripe id; the drivers had 0 runs, 0 run assignments and 0 schedule slots; seat capacity and roster versions were unchanged (nothing reserved).

## Migration rollout — 2026-10-31

Applied so far: `routeride_dev` and the dedicated test databases only. No staging or production credentials, database URLs or cloud CLI are available to the agent, so nothing beyond local databases has been touched.

The only path to shared environments is `.github/workflows/deploy.yml` (runs on push to `main`):

1. `deploy-staging` deploys the new API image to ECS but has **no migration step**. The new code needs the `operating_city` and pending-request columns, so a staging database that has not been migrated by other means will fail against the new image.
2. `deploy-production` is gated on `smoke-staging` passing, and it is the only job that runs the migration (`prisma:migrate` against `PROD_DATABASE_URL`, before the ECS deploy, which is the correct order). A failing staging smoke test therefore stops production from ever being migrated.
3. The production job pins `pnpm` version 9 while `package.json` pins `pnpm@11.5.1`; the CI workflow uses `prisma migration check` plus `--show` before applying, which the deploy job does not.

Decision needed before pushing: how the staging database is migrated (add a pre-deploy migration step to `deploy-staging` using a staging database secret, or migrate it by hand first).
